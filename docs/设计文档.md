设计一个初始Agent

### 目录

- code_agent.py: Agent唯一入口，负责加载配置、提示词、工具和运行模式
- prompts/common/: 普通任务使用的四个提示词文件
- prompts/optimization/: 四个方向优化提示词和一个assemble提示词
- tools/: 按工具分别存放工具实现，启动时自动扫描和加载
- utilities/: 模型适配、提示词组装、会话管理、轨迹记录和TUI
- config.yaml: 模型连接、重试和会话记录等配置
- 会话目录由外部框架通过请求上下文提供

Agent运行在Windows和Linux环境。Windows命令工具使用PowerShell 5.1，Linux命令工具使用Bash。

### Tools

所有工具派生自同一个基类。基类只保存工具定义，不保存某次调用的可变状态。

工具基类包括以下属性和方法：

- name: 工具名称，str
- guide: 提供给Agent的使用说明，str
- input_schema: 原生function calling使用的JSON Schema，dict
- execute: 接收请求上下文、参数和超时时间并执行工具

工具的每次调用创建独立的ToolCallRecord，记录request_id、session_id、model_call_id、batch_id、tool_call_id、实际参数、超时时间、结果和起止时间。多个并发调用不共享调用记录。

工具按以下目录结构存放。Agent启动时扫描tools下的工具目录，导入其中的工具类并注册；工具名重复、Schema无效或导入失败时，启动报错并记录文件路径。

```
tools/
  base.py
  edit/
    tool.py
  bash/
    tool.py
```

每个工具的参数都包含timeout。模型未提供该参数时使用60秒。timeout是正整数秒，模型可以为单次调用修改，没有Agent内的上限。参数缺失时使用默认值，非正整数作为该工具调用错误返回。

每次调用使用相同的结果结构：

```json
{
  "status": "completed",
  "stdout": "",
  "stderr": "",
  "exit_code": null,
  "error": null,
  "timeout_seconds": 60,
  "timed_out": false,
  "started_at": "",
  "ended_at": "",
  "duration_seconds": 0,
  "artifacts": {}
}
```

status取completed、error、timeout或cancelled。命令正常退出但exit_code非零时，status仍为completed，由模型根据退出码和输出判断命令或测试是否通过。无法启动工具、工具内部异常时使用error。超时使用timeout并设置timed_out为true。时间使用UTC时间戳，duration_seconds使用单调时钟计算。artifacts保存文件路径、差异文件等工具产物引用；没有产物时为空对象。

模型使用原生function calling调用工具。一次模型响应包含多个工具调用时，Agent同时启动全部调用，不设置Agent内并发上限。每个调用独立计时和处理错误。Agent等待本批所有调用结束后，按模型返回的调用顺序将结果交还模型。超时或失败的调用不影响本批其他调用。

#### Edit

Edit用于查看文件或目录、创建文件、整体覆盖文件，不支持局部替换或按行编辑。

- 相对路径以请求上下文中的workspace_root为基准。
- 查看文件时返回带行号的文件内容；查看目录时列出两层以内的非隐藏路径。
- create只创建不存在的文件；edit只覆盖已经存在的文件。两种操作都要传完整文件内容。
- 执行读写前解析规范路径和符号链接，并按请求上下文的读写范围检查权限。
- 路径越界或写入只读范围时拒绝操作，并按统一结果结构返回错误。
- 修改文件时记录目标路径和diff引用，查看文件时记录读取路径。

#### Bash

Bash是模型看到的工具名称。实际Shell由请求上下文决定：Windows使用PowerShell 5.1，Linux使用Bash。

- 每次调用启动独立Shell进程，默认工作目录取请求上下文中的working_directory。
- cd、环境变量和Shell状态不跨调用保留。
- 记录完整命令、标准输出、标准错误和退出码。
- timeout到期后终止该调用的Shell和整个子进程树，返回timeout结果。其他并行调用继续执行。
- 工具指南和系统提示词要求命令只访问请求上下文允许的工作区。Bash自身不提供操作系统级路径隔离，外部框架负责强制隔离。

### Prompts

基础提示词分为任务执行和自我改进两类。Agent根据mode选择提示词。

#### 任务执行提示词（prompts/common/）

普通任务固定读取以下四个文件，并按顺序组装：

1. 01_efficiency_guide.md：减少重复调用；只并行发起可以同时执行的工作；可通过timeout延长耗时较长工具的执行时间。
2. 02_exploration_guide.md：修改前查看相关文件，了解目录结构、调用关系和现有约定。
3. 03_code_generation_guide.md：根据问题和代码库实现修改，优先保持改动范围清晰。
4. 04_validation_guide.md：选择相关测试或检查命令；根据错误结果修复并重新验证。

初始文件应保持简洁，只写完成当前任务所需的规则。四个文件今后可由自我改进Agent修改内容，但文件名和文件数量固定；不得新增、删除或重命名common目录中的提示词文件。其他Markdown文件不加载。

工具列表由已注册工具的name和guide自动生成。各工具的input_schema通过模型API的原生tools字段单独传入。

系统提示词由身份骨架、四个任务提示词和工具指南组成。用户消息包含请求文本及必要的运行上下文摘要和路径。请求上下文对象由外部框架提供，不可由Agent改写。

```markdown
System:
You are a coding agent. Finish the user's request using the following instructions.
[执行效率引导]
[代码探索引导]
[代码生成引导]
[代码验证引导]
There are the available tools you can use:
[工具名称和指南]

User:
[用户请求]
[必要的上下文摘要和数据路径]

Tools:
[已注册工具的原生Schema，由API单独传入]
```

#### 自我改进提示词（prompts/optimization/）

以下五个文件各自是一条完整提示词：

1. 01_efficiency_optimization.md：效率优化，对应o_1模式。
2. 02_exploration_optimization.md：代码探索优化，对应o_2模式。
3. 03_code_generation_optimization.md：代码修改优化，对应o_3模式。
4. 04_validation_optimization.md：测试生成与验证优化，对应o_4模式。
5. 05_assemble_guide.md：整合已采纳优化方向的改动，对应assemble模式。

前四个提示词说明本方向的优化目标、奖励函数、当前Agent及轨迹输入，并引导Agent修改对应的common提示词和相关工具。Agent可以修改其他实现，包括工具、utilities和依赖。方向提示用于引导修改，不限制可改文件。

优化模式初始消息提供本轮基线、评分摘要、轨迹摘要、完整数据路径，以及本方向前两轮尝试的代码diff、样例轨迹、得分和采纳结果。摘要和历史记录由外部调度器准备；Agent可以使用工具按需读取原文。

各优化提示词必须写入本方向的奖励计算公式及指标含义。代码修改奖励的验证轮次项为减项，即r_code,i = p_i - GRPO(n_i)。测试生成奖励中的验证轮次项也为减项，按实验定义备注修正正文页留存的加号。五项指标归一化和加权分数按实验定义计算；每个候选使用自己的权重。得分计算和改进采纳由外部调度器完成，Agent读取结果，不自行改变评分规则。

prompts/optimization/中的五个文件是受保护文件。Agent提示词明确禁止修改这些文件。外部调度器记录初始哈希，并在Agent退出后检查和恢复被修改的文件。

assemble模式使用外部框架提供的工作区：基础Agent目录和被采纳方向的候选目录只读；外部框架预先创建基础Agent的输出副本，Agent只修改该输出目录。用户消息包含各候选方向、对应得分和路径。合并冲突无法解决时，保留可用实现，并在最终报告中列出冲突。

自我改进提示词的组装形式如下：

```markdown
System:
[当前优化模式的完整提示词]
[工具名称和指南]

User:
[本轮目标、基线得分和优化方向]
[本方向前两轮的摘要、得分、采纳结果和数据路径]
[本轮完整轨迹和代码diff的路径]

Tools:
[已注册工具的原生Schema，由API单独传入]
```

### utilities

utilities负责模型API适配、提示词组装、工具注册、会话和轨迹保存、恢复、命令行参数解析及TUI。

1. 模型接口支持OpenAI Compatible、OpenAI Responses和Anthropic Messages三种原生function calling格式。三个接口均使用流式响应，默认启用，不提供关闭选项。OpenAI Compatible服务必须支持流式工具调用。
2. 三种接口转换为Agent内部统一的消息、工具调用和工具结果格式。流式工具参数收齐并确认响应正常结束后才执行；流中断时丢弃未完成的工具调用。
3. TUI实时显示模型文本和工具执行状态。headless模式通过参数传入任务。两种模式都使用同一运行循环和工具实现。
4. 通过mode参数区分common、o_1、o_2、o_3、o_4和assemble六种模式。该参数决定提示词；工作区路径和权限来自外部请求上下文。
5. 模型连接信息通过config.yaml配置provider、model、base_url和api_key。密钥直接填写在对应provider的api_key字段，不通过环境变量读取。无需认证的OpenAI Compatible服务可以留空。config.yaml不纳入Git跟踪。
6. 每次API请求的超时时间默认300秒，可配置。网络异常、请求超时、HTTP 429和HTTP 5xx错误使用指数退避重试，默认最多重试3次，不含首次请求；重试次数、退避基数和最大等待时间均可配置。认证失败、无效参数和其他不可重试错误直接记录并退出。流中断后可重试该API请求，不执行未完成的工具调用。重试耗尽后保存会话和轨迹并退出。
7. 模型调用轮数不设上限。无工具调用的完整模型响应作为最终回答，任务正常结束。用户中断或外部框架取消时，停止接收新调用，终止正在运行的工具进程树，保存已有记录并以cancelled状态结束。
8. 历史会话支持TUI的/resume和headless的--resume。会话按JSONL追加保存，每条事件写入后立即落盘。恢复时使用原mode、provider和model，并验证当前请求上下文的request_id和工作区与保存记录一致。已启动但没有记录完成结果的工具调用标记为interrupted，不自动重复执行；后续模型调用会收到该调用状态未知的结果。
9. code_agent.py是Agent唯一入口。无头调用通过--mode、--context、--prompt或--prompt-file指定模式、外部请求上下文和任务；--resume指定恢复的会话。TUI和无头模式都必须收到外部提供的请求上下文。

### 请求上下文与运行边界

外部框架在启动Agent前创建隔离环境，并提供只读请求上下文。Agent不创建、销毁或管理隔离环境，也不改变上下文内容。上下文至少包含：

- request_id和session_id
- workspace_root和working_directory
- platform和shell
- 允许读取、允许写入和只读路径范围
- 会话记录目录

assemble模式还提供基础工作区、候选工作区及可写输出工作区的路径和访问策略。Agent使用这些路径，但不负责复制或创建工作区。

文件工具在内部检查规范路径、符号链接和读写策略。Bash的提示词和默认工作目录限制其预期操作范围；实际的系统级隔离由外部框架执行。

### 运行流程

1. code_agent.py读取配置、mode和请求上下文，检查模型配置、工作区路径及读写范围。
2. 工具管理器扫描并注册工具，按mode读取提示词并组装system消息。
3. 模型以流式方式返回文本或原生工具调用。Agent保存该次模型调用的think事件。
4. 响应没有工具调用时，将完整文本作为最终回答并结束。
5. 响应有一个或多个工具调用时，为每个调用创建独立action事件和ToolCallRecord，并同时执行。
6. 每个调用完成后立即保存结果。本批全部结束后，按原始调用顺序把统一结果返回模型，开始下一轮。
7. 单个工具错误或超时只结束该工具调用。统一错误结果交给模型，模型决定是否重试、调整参数或结束任务。
8. API不可恢复错误、用户中断或外部取消时，按各自终止状态保存会话和轨迹。

### 轨迹记录

Agent把原始轨迹按JSONL保存。轨迹事件包含think和action两类，使用唯一event_id，以及request_id、session_id和父调用标识。

think事件对应一次完整模型响应，至少记录：

- provider、model和model_call_id
- 模型返回的文本；接口实际提供时记录reasoning文本，否则记为null
- 开始时间、结束时间和单调时钟耗时
- input_tokens、output_tokens和reasoning_tokens；接口未提供的字段记为null
- 本次响应包含的工具调用ID

工具调用可能共享一次模型调用和Token用量。Token记录在think事件上一次，action事件通过model_call_id引用，不重复计数。思考内容由接口实际返回内容构成，不推断接口没有提供的文本。

action事件对应一次工具调用，至少记录：

- tool_call_id、model_call_id、batch_id、工具名称、输入参数和timeout_seconds
- 开始时间、结束时间和单调时钟耗时
- 统一工具结果的status、stdout、stderr、exit_code、error、timed_out和artifacts
- 工具实际报告的文件路径和diff引用

Agent保存完整原始事件。外部调度器负责阶段划分、依赖边、并行批次和验证轮次计算、长文本摘要及奖励计算。思考文本超过1000个Token时，调度器在优化输入中提供摘要和原文引用。

工具调用的原始参数、输出、ID和时间用于后续建图。可以确认的文件读写记录在artifacts中；不能确认的文件访问不伪造为精确路径。外部评估按轨迹阶段区分探索操作与验证命令。

### 稳定性与恢复

API错误按config.yaml配置重试。每次尝试分别记录开始时间、结束时间和错误。流式响应只在收到完整结束信号后写入正式消息历史；中途断开时，未完成响应不进入下一轮上下文。

工具超时由工具运行器终止当前调用的进程树，并按timeout结果返回模型。取消任务时，Agent停止派发工具调用并终止仍在运行的进程。工具命令已经启动但结果尚未落盘时，恢复程序将其标记为interrupted，避免不确定的副作用被自动重复执行。

会话文件记录原生API所需的统一消息、工具调用和结果。恢复只允许使用原会话的mode、provider和model；请求ID或工作区不一致时拒绝恢复。API密钥从当前环境变量重新读取。

### 外部框架职责

外部框架负责准备和隔离工作区、生成请求上下文、提供评测任务和奖励数据、保存版本快照、恢复受保护的优化提示词，以及根据原始轨迹计算图结构和奖励。Agent负责执行模型请求、工具调用、任务内文件操作和记录原始轨迹。
